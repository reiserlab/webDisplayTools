What this stage is

Frank proposed building the bridge's device connectors on ROS 2 (Plan B) instead of inside the Python bridge (Plan A). The spike exists so the choice can be made on measured data rather than on the plans. It keeps bridge 3.4 installed beside it, keeps the browser protocol identical, and adds the three things Plan B promised: a record of truth in MCAP, typed messages, and a graph that any ROS tool can look at. The decision itself has not been made.

The graph

Five processes on one machine. Only the bridge node talks to the Studio, over the same WebSocket as bridge 3.4. Programs that are not ROS (FicTrac, the BIAS camera app, the simulator) stay outside the graph and are wrapped by one small adapter each.

What a run records

While a run's log is open, the bridge node writes one bag. Device topics go in as received. Three streams only the bridge can produce go in beside them, each carrying the writer's emission sequence number so the derived log keeps today's line order.

/arena/frame

One record per FicTrac frame: the index the display was asked to show, with the closed-loop node's own sample time. Reconstruction uses that clock, never the recorder's.

/arena/browser

Every message the Studio sent, verbatim, with its receive stamp: config, log events, controller telemetry rows, connector commands, the export request.

/arena/event · /arena/session

bias_config, heading_tare, connector status, source lost or resumed, warnings; the run's open and close with the one millisecond base.

The converter

Pure Python, no ROS process: bag in, behavior_v2 or v1 or full out. Reads a crash-torn bag. The Studio's log_export now answers with its output.

The experiment-shaped test: color optomotor

For the rig test the lab wanted a real experiment rather than the closed-loop demo: the G6 version of its Protocols 11 and 13. Open-loop rotating square-wave gratings, clockwise then counterclockwise, 20 s trials, a camera timestamp at the start of every trial and one video for the run. Two things are new on the four-color G6 panels: each pattern lights one LED color only (the panels carry four colors in every 2×2 pixel cell; a pattern that lights one bank's pixels drives one color), on the top panel row only, and the brightness comes from the per-trial duty override rather than from the pattern. One spatial period (20 px, 36°), one speed (80 frames/s, 4 Hz), three duties (25, 50, 100 %), four colors, two directions, two repetitions: 48 trials, about 18 minutes with the 3 s dark intervals.

A two-minute smoke variant (10 s per pattern, duty 100 %, same camera bracket) ran on the bench through the graph with the real BIAS app after the branch had been brought up to the Next release: 17 of 17 steps, no errors, 13 camera replies all ok with timestamps 12 s apart, every trialParams carrying duty: 255 and its pattern resolved by name to the card slot, runlog-check OK, and the run's bag re-indexed to 156 kB. On Windows the same protocol is step 5c of the test plan.

How to run it

cd ros2-poc
pixi install                       # default: String topics, always installs
pixi install -e typed              # optional: builds the .msg package (needs a compiler)
pixi run rig -- --sim --bias --bias-args "--video-dir /abs/path"
python ../.claude/nocache-server.py 8092      # the Studio of this branch, from the repo root
# Chrome: http://localhost:8092/arena_studio.html?p=bias_camera_closed_loop_poc&rig=cshl_g6_2x10_ball
pixi run export                    # closes the run's bag and writes the converted log
pixi run test                      # the 46-check harness, no hardware

How to look at it

Foxglove turned out to be the piece that makes "the bag is the record" tangible. It opens a run's MCAP directly with no ROS installed, reads the schemas rosbag2 embedded, and with the layout file in docs/ shows the displayed frame index, heading, bias and epoch as time series over the same playhead as the Studio's own messages and the camera replies. The same layout works live: pixi run rig -- --foxglove starts a bridge on port 8766 beside the graph. To make the live view useful the bridge now also publishes the two channels the Studio scope derives in the browser, turning rate and forward velocity, as typed fields of every frame. One consequence of the crash-safe writer was that a fresh bag has no index and Foxglove flagged it; the bridge therefore rewrites a bag indexed and zstd-compressed the moment a run closes cleanly (the bench bag went from 6.8 to 2.3 MB in 0.18 s, same records).

What is still open

  • The branch now includes the Next release (Studio v0.95 with the SD-upload fixes); the only merge conflicts were the footer line and the release-notes entry. On that build the Console panel's bridge Connect button did not open a socket while the client's own connect did; to check tomorrow.
  • BIAS on the Mac writes MJPEG whatever the filename asks for (516 MB for the 100 s smoke run); the Windows build's own logging format setting decides whether the ufmf comes out.
  • Windows, where most rigs live: the install, the typed build, BIAS with a FLIR camera, a real FicTrac. The step-by-step is ros2-poc/WINDOWS-TEST.md.
  • The closed-loop math still runs inside the bridge node. A separate process is Plan B's full shape; the spike measured the ordering cost it would bring (17 same-millisecond swaps in 3949 lines, readers unaffected).
  • The Studio asks the bridge to export only when it commits to the course repo; otherwise the bag stays open until the next run. A real Plan B bridge should close the bag at run end.
  • Serving this Studio from GitHub Pages at /ros/ needs the small deploy-tooling change on main first; the lab test serves it from the checkout instead.
